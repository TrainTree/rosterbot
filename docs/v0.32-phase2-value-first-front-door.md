# RosterBot v0.32 Phase 2 — Value-First Front Door

## 1. Old versus new first 30 seconds

Previously, a fresh user arrived at “Let’s set up your role & schedule” and immediately faced the full manual setup model: dates, pay classification, scheduling mode, depot, roster and line. The first configured dashboard—the strongest proof of value—appeared only after those decisions and a roster preview.

The new fresh-user experience begins with the outcome:

> Know what you’re working and what you should be paid.

It then explains that roster, diary and expected pay live together and that the working copy remains available offline. A single dominant **Try RosterBot** action reveals useful sample value without requesting personal information. Manual setup, reference browsing and returning-user recovery remain available, but no longer compete equally for attention.

Configured users continue directly to Home and do not see this front door.

## 2. Chosen product promise and copy

The chosen promise is:

> Know what you’re working and what you should be paid.

Supporting copy:

> Your roster, diary and expected pay together in one place, with your working copy available offline.

This is direct, driver-centred and limited to capabilities RosterBot provides today. It does not imply automatic published-roster ingestion or change detection.

## 3. Front-door hierarchy

The hierarchy is intentionally unequal:

1. **Try RosterBot** — primary, one-tap, no commitment.
2. **Set up my roster** — visible secondary action for a user already convinced.
3. **Browse rosters & shifts** — a full-width reference action below the hero.
4. **Already use RosterBot?** — a collapsed returning-user disclosure containing sign-in/restore and backup restore.

At 390 × 844, the promise, both Try/setup actions, browse action, and “no account or personal details needed” message are visible in the initial viewport. The measured browse card ends at 706 CSS px with zero horizontal overflow.

## 4. Demo architecture and isolation guarantees

The example is presentational DOM controlled by the navigation layer. It does not mount a fake roster, populate setup controls, invoke the roster engine, register sample values, or create a fake schema-5 user. Its only runtime state is an HTML class and same-document browser-history state so Back/Forward and reload remain understandable.

Verified isolation:

- canonical generation remained 1 → 1;
- localStorage was byte-for-byte unchanged during entry, use and exit;
- IndexedDB values were unchanged and direct IndexedDB write instrumentation recorded zero writes;
- no Cloud, account, calendar or backup API is invoked by sample transitions;
- refresh, Back/Forward, rotation, repeated entry/exit and cold offline reopen create no personal state;
- a new cold reopen returns to the clean front door; the user may enter the sample again offline;
- sample information cannot appear in an exported backup because it never enters a registered persistence surface.

## 5. Sample contents and rationale

The explicitly fictional example shows:

- a concrete Today duty with start/end time and duration;
- Tomorrow as an Off Roster day and the next upcoming duty;
- a compact two-calendar-week, Sunday–Saturday SCS C-roster preview using official lines 60 and 61, actual dates and the live roster heading format;
- current-fortnight hours and expected gross pay;
- diary/correction, pay-check, calendar and offline benefits;
- a natural **Set up my roster** conversion action.

These elements reproduce the value pattern identified in Phase 0A—Today, upcoming work, Off Roster days, forward roster visibility and expected pay—without pretending to be a live or automatically sourced personal roster. The preview resolves official SCS C-roster lines 60 and 61 for the current and following calendar weeks and labels them in the live `C · LINE …` / `WC …` format. Compact cells use `OR` while full copy uses `Off Roster`; `Rest` is deliberately not used as a synonym. “Example roster”, “fictional sample information”, and “nothing has been saved” are shown explicitly.

The two-week preview makes sign-on time the primary scanning value and sign-off secondary while retaining the weekday and actual calendar date. Every preview day, plus the example Today card, opens the same small read-only fictional duty dialog. A workday shows its official date, duty code, combined sign-on/sign-off range, duration and shift-book content; an OR day simply explains that it is Off Roster. Expected gross is calculated by the real PayBot engine for a fully qualified driver (`PB205`) using those official sample duties. The dialog uses the shared Phase-1 controller for focus containment and restoration and exposes no diary, pay, notes, Cloud or actual-work controls.

The sample cards use the same `--surface-2`, `--border`, `--text`, `--muted` and `--accent` design tokens as configured Home. They therefore follow every supported RosterBot theme and colour mode instead of maintaining a parallel demo palette.

## 6. Roster Lookup and browse separation

The old temporary Roster Lookup entry reused personal setup and therefore required nearly the same decisions as creating a roster. It has been replaced by **Browse rosters & shifts**, which directly opens the existing read-only master-roster and shift-book viewer.

The browse flow requires one interaction and asks for no pay classification, role-effective date, account, timeline or roster acceptance. Closing the viewer restores focus to the Browse action and leaves persistence unchanged. The configured-user Roster hub now uses the same honest browse concept rather than maintaining two overlapping lookup cards.

## 7. Returning-user treatment

Returning-user actions remain on the first screen but are placed in a collapsed **Already use RosterBot?** disclosure. Expanding it reveals:

- **Sign in & restore**;
- **Restore a .rosterbot backup**.

No Cloud or import semantics changed. This keeps recovery discoverable without implying that a new user needs an account before trying RosterBot.

## 8. Early trust messaging

Before any personal question, the UI now states in ordinary language that:

- no account is required for ordinary use;
- the roster can stay on this device;
- Cloud Sync is optional;
- entering roster details does not automatically upload them;
- installed RosterBot continues working offline.

The primary message contains no Supabase, schema, attestation, revision, token or cryptographic implementation terminology.

## 15. Known issues and deliberate boundaries

- The full manual setup form is still decision-heavy. Phase 2 labels it honestly but does not redesign it.
- Sample pay is fixed fictional presentation, not a live calculation. This is deliberate isolation, not a fake personal roster.
- The master-roster browser retains its existing dense table on small phones; it is functional and non-canonical, but broader viewer ergonomics may be reviewed later.
- A compact four-week forward calendar is a candidate for the Phase 4 Home/dashboard UX review. Phase 2 deliberately stops at two calendar weeks to keep the first sample immediate and uncluttered.
- Consider giving the real configured Today/day cards a lightweight read-only shift-detail view before or alongside the full actual-day editor. Phase 2 leaves the configured Today → actual-day workflow unchanged so that decision can be made deliberately during the Phase-4 Home/Diary review.
- Browser history is used only for in-session first-run view transitions. Demo data itself is never persisted; a fresh cold reopen returns to the front door.
- Release/version metadata remains on the accepted development baseline and should be handled with the eventual v0.32 release-candidate hygiene rather than mixed into this UX phase.

One integration defect found during regression was corrected before completion: configured-dashboard rendering initially used an unnecessary history replacement, which made backup import appear to navigate twice. Removing that write restored the exact one-reload import contract without weakening first-run Back/Forward support.

## 16. Recommendation for Phase 3

Phase 3 may redesign the manual setup journey behind **Set up my roster** while preserving:

- the value-first front door and one-tap isolated example;
- genuine non-canonical roster browsing;
- returning-user separation;
- concise local/optional-Cloud trust promise;
- preview-before-save and **Use this as my roster** confirmation;
- Phase 1’s one-decision/one-generation transactional acceptance.

Priority should be reducing decisions before the personal preview, deferring pay/employment detail until its benefit appears, and progressively revealing alternation/manual-pattern/leave complexity. The demo must remain independent of any future setup restructuring.
