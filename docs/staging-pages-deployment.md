# v0.30 dedicated GitHub Pages staging deployment

This runbook creates an HTTPS staging origin for real-device testing without
changing or deploying the production `rosterbot.work` site.

## Chosen structure

- New repository: `TrainTree/rosterbot-beta`.
- Pages source: `main` branch, repository root.
- Custom domain: `beta.rosterbot.work`.
- Repository contents: deploy-only static runtime bundle, not the source
  worktree, tests, backend captures, Supabase migrations or local tooling.
- Production repository and origin remain `TrainTree/rosterbot` and
  `rosterbot.work` respectively.

A separate repository is required because one GitHub repository has one Pages
site/custom-domain configuration. A branch in the production repository would
not create an independently configured second Pages site.

## Prepare the deploy-only bundle locally

From the v0.30 worktree:

```sh
staging_dir="$(mktemp -d)/rosterbot-beta"
PHASE10B_BETA_PUBLISHABLE_KEY="<isolated staging sb_publishable_ key>" \
  node scripts/prepare-staging-pages.mjs "$staging_dir"
```

The command refuses to overwrite a non-empty directory. It copies only
`index.html`, `.nojekyll`, and the `css`, `data`, and `js` runtime directories;
writes a staging-only `CNAME`; replaces the ordinary production deployment
profile with an exact `https://beta.rosterbot.work` / isolated-staging profile;
verifies local asset references and the schema-5 capability gate; scans the
entire output for production Supabase identifiers and privileged/JWT
credentials; and creates fresh SHA-256 checksums. The key is required through
the environment so the staging credential is not hard-coded into ordinary
production source.

The generator accepts only a modern `sb_publishable_` browser credential. It
rejects missing, malformed, legacy-JWT, secret and service-role inputs before
creating the output directory. The beta runtime ignores saved Cloud connection
configuration and fails closed unless its origin is exactly
`https://beta.rosterbot.work` and its profile URL/ref/origin contract validates.

Review before any Git operation:

```sh
find "$staging_dir" -type f -print | sort
sed -n '1p' "$staging_dir/CNAME"
shasum -a 256 -c "$staging_dir/SHA256SUMS.txt"
```

Expected `CNAME` content is exactly `beta.rosterbot.work`.

For a Step 7B redeployment, also compare the generated runtime files with the
committed source hashes, confirm Cloud fallback and saved-configuration
override are disabled, and record the generated `SHA256SUMS.txt`. Push only
that reviewed output to `TrainTree/rosterbot-beta/main`. After GitHub Pages is
live, fetch each hosted runtime asset and require an exact checksum match
before enabling staging capability 5 or creating synthetic test users.

## Step 7B approval boundary

The repository, Pages site, custom domain and DNS were established in the
earlier approved beta deployment. Stop here until separate Step 7B approval is
given to push a replacement deploy-only bundle and exercise it against
isolated staging. The preparation script itself performs no Git, GitHub, DNS,
Auth, database or capability mutation.

## Initial GitHub setup reference

1. In the `TrainTree` GitHub organization, confirm `rosterbot.work` is verified
   under **Organization settings → Pages → Verified domains**. If it is not,
   add it and publish the exact TXT value generated by GitHub at
   `_github-pages-challenge-TrainTree.rosterbot.work`. Keep that TXT record.
2. Create `TrainTree/rosterbot-beta`. A public repository is the simplest Pages
   option. Do not change `TrainTree/rosterbot`.
3. Initialize the reviewed staging bundle as the new repository's `main`
   branch, commit it, and push only to the new repository. The staging `CNAME`
   must be present in this first commit, before Pages is enabled.
4. In `TrainTree/rosterbot-beta` open **Settings → Pages**. Select **Deploy from
   a branch**, branch `main`, folder `/(root)`, then save.
5. In the same Pages settings, set the custom domain to
   `beta.rosterbot.work` before adding the DNS record. The committed `CNAME`
   already contains that exact value.
6. At Porkbun, create an explicit record:

   | Type | Host | Answer | TTL |
   |---|---|---|---|
   | CNAME | `beta` | `traintree.github.io` | 600 initially |

   Do not add the repository name to the CNAME target. Do not alter the apex
   `A` records or the existing `www` CNAME used by production.
7. Wait for the Pages domain check and certificate issuance, then enable
   **Enforce HTTPS** for the staging repository.
8. Verify `https://beta.rosterbot.work/` and compare its runtime asset hashes
   with the reviewed bundle. Test in a fresh browser profile so production and
   staging storage cannot mix.

Do not test through a project path under `rosterbot.work`. GitHub can expose a
project Pages site beneath an account's existing custom domain when the project
has no custom domain of its own. Keeping `beta.rosterbot.work` in the first
commit and completing the repository custom-domain setting before testing
avoids using the production browser origin.

The DNS zone currently has a wildcard Porkbun parking record resolving unused
subdomains to `pixie.porkbun.com`. The explicit `beta` CNAME must replace that
wildcard answer for this name. GitHub recommends avoiding wildcard records; it
can be removed separately after confirming it is not intentionally used, but
removing it is not required to configure the explicit staging name.

## Cloud safety

The staging bundle does not contain server migrations and does not change the
production Supabase project or its capability. The v0.30 client retains its
schema-5 transfer hold while staging advertises capability 4. Capability 5 can
release only after a fresh authenticated attestation validates the exact
beta/staging environment, project, contract and writable range; the grant is
session-scoped and is revoked on authentication or trust-binding changes.
Because `beta.rosterbot.work` is a different origin from `rosterbot.work`, it
receives separate localStorage, IndexedDB, cookies and service state.

Do not use production user accounts or production backups on staging. Use only
synthetic fixtures. Do not change either project's capability or modify the
production Pages repository as part of bundle preparation/deployment.
