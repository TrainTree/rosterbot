# Phase 11A — v0.30.0 production release candidate

Status: **release candidate prepared; production unchanged** on 2026-10-09
(Australia/Melbourne).

Phase 11A changed no production data, schema, Auth configuration, capability,
client asset, repository branch, tag or release. The only production access was
the guarded read-only preflight in
`backend-capture/phase11a/production-preflight-readonly.mjs`.

## Release candidate

The production runtime is generated by:

```sh
node scripts/prepare-production-pages.mjs <empty-output-directory>
```

The generator copies only `.nojekyll`, `CNAME`, `index.html`, `css/`, `data/`
and `js/`, then creates `SHA256SUMS.txt`. Tests, synthetic fixtures, Supabase
deployment tooling, captured backend evidence, documentation and scripts are
not runtime-bundle inputs.

The production profile is fixed to:

- primary origin `https://rosterbot.work`;
- documented alias `https://www.rosterbot.work`;
- project `rithmbggiiusrmdcqrif`;
- URL `https://rithmbggiiusrmdcqrif.supabase.co`;
- the existing browser-safe production publishable key;
- schema-5 client capability requested, but every schema-5 Cloud transfer held
  until a fresh authenticated attestation matches the profile and advertises
  the approved `rosterbot-schema5-cloud-v1` contract with capability 5.

Saved configuration and fallback are disabled. A production bundle on any
other origin is Cloud-disabled. A beta deployment profile cannot validate with
either production origin. The generated bundle must contain exactly one
browser credential and no staging ref, URL, origin or additional credential.

first mismatch.

   release-candidate worktree.

10. After the production client, server contract and capability-5 canary all

## Rollback

- Before the client is deployed, abort without mutation on any audit failure.
- If hosted assets differ while capability is still 4, keep capability 4 and
  repair the Pages deployment from the reviewed commit.
- Do not roll the client back to v0.29 after any user may have loaded v0.30:
  local schema-5 state must not be opened by an older writer. Keep v0.30
  deployed and fix forward.
- If the server-contract transaction fails, its transaction must roll back and
  capability must remain 4. Do not attempt capability 5.
- For any security/data-integrity failure after capability 5, first use the
  reviewed exact-ref rollback transaction to change only `4..5` back to
  `4..4`. Keep the v0.30 client deployed in fail-closed local-only mode, retain
  the schema-5 server validator/attestation functions, stop rollout and
  preserve evidence. Do not downgrade database rows or compatibility
  projections.
- Tagging/release publication occurs only after the complete production pass;
  otherwise no tag is created.
