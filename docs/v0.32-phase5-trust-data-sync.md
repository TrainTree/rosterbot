# RosterBot v0.32 Phase 5 — Trust, Backup & Data Sync UX

## 1. Baseline

Phase 5 started from the accepted Phase 4 source commit `5aaaca624d7f88f44d021c4bb8f81a86b8920d02` on `experiment/v0.32-ux-adoption`, with a clean worktree. Production was not opened, contacted, changed, or deployed.

## 2. Old versus new Data & Sync structure

The old modal presented local storage, backup, account authentication, encryption, sync comparison, revision history, manual recovery, provider configuration, and diagnostics largely in implementation order.

The primary surface is now organised around five user jobs:

1. **Your working copy is on this device**
2. **Keep a backup of my RosterBot**
3. **Use RosterBot on another device**
4. **Cloud Sync**
5. **Technical details**

The existing safe actions and identifiers remain in place. No persistence, Cloud, encryption, recovery, capability, or service-worker contract changed.

## 3. Primary user mental model

The modal now leads with the truthful local-first outcome: the working copy is saved on this device, ordinary use needs no account, local changes work offline, and entering roster/diary/pay information does not upload it.

It then explains resilience without making local use sound unsafe: a user who loses the device or clears its site data needs either a backup file or an available Cloud restore path.

## 4. Backup wording and workflow

Manual backup is presented as **Keep a backup of my RosterBot**. A `.rosterbot` file is described as a point-in-time copy kept somewhere the user controls. The primary actions are now **Download .rosterbot backup** and **Restore from backup**.

The import flow still stages and validates before replacement, retains full-replacement semantics, uses the transactional schema-5 replacement path, rolls back exact bytes on failure, and preserves recovery evidence. Its preview now leads with user-level contents and safety checks instead of app/schema vocabulary. Manual backup files remain plaintext; that fact remains explicit in technical/encryption guidance.

## 5. Another-device workflow

The new **Use RosterBot on another device** section gives two distinct routes:

- ongoing coordination across multiple devices through optional encrypted Cloud Sync;
- a one-time move or restore using a `.rosterbot` backup.

These route buttons only navigate to the existing safe action. They do not write personal state or start a Cloud transfer.

## 6. Account versus sync

The signed-out surface explicitly says Cloud Sync is off and nothing is being uploaded. Creating or signing into an account identifies the Cloud account but remains separate from the first sync decision. Local use continues without an account.

This remains separate from any future employee identity or authorised published-roster source.

## 7. Cloud status language

Primary states now describe outcomes and next actions:

- **Up to date**
- **Changes saved on this device**
- **Another device has newer changes**
- **Sync needs your choice**
- **Offline — changes saved on this device**
- **Sign in again**
- **Unlock to sync**
- **Sync temporarily unavailable**
- **Cloud Sync needs attention**

Network, timeout, auth loss, capability hold, encryption lock, verification failure, and revision conflict remain distinct typed states. Normal connectivity errors state that the working copy remains safe on this device.

## 8. Encryption wording

The primary encryption card now explains whether the synced copy is encrypted, locked, unlocked for this session, or remembered on this device. It explains the passphrase/recovery-key consequence before protocol detail. Algorithm and key identifiers no longer dominate the primary state.

The existing encryption format, key wrapping, remembered-device behaviour, verified-unlock publication, logout/auth/user/config revocation, and restore validation are unchanged. Scope and remembered-device evidence remain under **How encryption works on this device**.

## 9. Backup versus Cloud

The modal directly distinguishes:

- **Backup:** a point-in-time file the user keeps;
- **Cloud Sync:** ongoing coordination between supported devices when enabled.

Neither is presented as mandatory. Cloud Sync does not replace the working copy on each device, and the UI does not imply that an account alone uploads data.

## 10. Error and conflict wording

Conflict copy now states that both copies are safe and that RosterBot will not overwrite either automatically. Offline/transport/auth/encryption/capability states describe the immediate action in ordinary language. Existing deliberate device-versus-Cloud choices, expected-revision enforcement, RB003 handling, and fail-closed recovery paths remain authoritative.

Safe Data Recovery remains a separate integrity state and was not turned into an ordinary sync warning.

## 11. Technical details

Revision numbers, hashes, schema compatibility, provider/project binding, capability evidence, Cloud history, manual recovery actions, and storage diagnostics remain available in expandable technical areas. The ordinary user no longer needs them to answer where data lives or how to protect/move it.

## 12. Accessibility

Data & Sync continues to use the Phase 1 dialog controller. Initial focus enters the modal, background content is inert, keyboard focus remains contained, Escape/Close restore focus, and dynamically revealed controls remain in the task.

At 390 × 844 with a 200% root font:

- page horizontal overflow: `0 px`;
- dialog width: `370 px` within a `390 px` viewport;
- the modal body remains internally scrollable;
- route/comparison cards reflow to one column.

The accepted iOS full-overlay, safe-area, VisualViewport, rotation, and keyboard geometry remained green.

## 16. Known limitations

- Browser/site-data eviction remains controlled by the browser/platform; RosterBot can explain and mitigate it but cannot guarantee retention.
- Manual `.rosterbot` backups remain plaintext and require the user to store them appropriately.
- Cloud account authentication remains email/password based and separate from any future verified employee identity.
- Provider configuration remains visible to power users because local/test builds need it; hosted fixed bindings remain authoritative.
- Destructive clear and some recovery confirmations still use established confirmation UI; broader accessible confirmation/dialog refinement belongs to Phase 6.

## 17. Future identity seams

The new information architecture leaves account authentication and Cloud Sync as one optional data-coordination job. A future employer-approved identity and authorised roster source can be introduced as a separate user job without pretending that Cloud Sync proves employee identity today.

No Microsoft/Entra, departmental identity, roster authorisation, wallsheet, or daily-roster ingestion was implemented or promised.

## 18. Recommendation for Phase 6

Phase 6 may proceed after human beta review. It should perform the broader accessibility pass—headings, accessible names, error association, status announcement, large-text refinement, and confirmation/task semantics—while preserving the Phase 1 dialog controller and all Phase 5 data-safety boundaries.
