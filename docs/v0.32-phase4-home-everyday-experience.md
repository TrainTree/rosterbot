## 2. Old versus new Home hierarchy

The source-informed audit found these previous Home components:

| Component | Source | User question | Previous prominence | Phase 4 treatment |
| --- | --- | --- | --- | --- |
| Search | universal-search controls and `20-roster-ui.js` | Find a known duty/date | First, visually dominant | Retained as a utility below daily and forward answers |
| My Roster card | `70-navigation.js` `renderWeek`, `renderFortnight`, `renderRosterCard` | What is my current roster/pay period? | Large combined card | Retained as the detailed-planning route, below the forward view |
| Today | `70-navigation.js` `renderToday` | What am I doing now? | Second card in a pager | Promoted to the first daily card |
| Expected pay | `PayBotCombined.previewFortnight` via `renderFortnight` | What should I be paid? | Embedded inside My Roster | Given a distinct daily-glance card beside next OR |
| Pay checks | `renderVariances` | Does a payslip differ? | Peer dashboard card | Retained lower down as a review utility |

| Day interaction | `RosterBotDiary.showDay` | Inspect and edit a day | Today immediately opened the actual-day editor | Viewing now opens read-only detail; editing is explicit |

The new information order is:

1. Today and Tomorrow.
2. Next Off Roster and expected pay.
3. Current calendar week plus three following weeks.
4. Search.
5. Detailed My Roster, pay checks, and diary history.

The application shell, configured-user identity, bottom navigation, full Roster view, Pay view and historical tools remain familiar.

## 3. Today design

Today is a first-class button with the date, duty identifier, sign-on/sign-off, duration and the current truthful source classification. Compact working-day content prioritises the duty and sign-on. An Off Roster day shows `OR` and the full text `Off Roster`.

If an actual-day record exists, Home uses the recorded duty and displays `Recorded actual`. If no actual exists, it describes official/master-rotation output as `Roster projection`; user-entered manual patterns use `Saved work pattern`. No weekly/daily published-roster status is implied.

## 4. Tomorrow design

Tomorrow uses the same compact card and source rules as Today. It is visible without opening a pay fortnight or full roster. Working, leave and Off Roster states are supported, and its read-only detail uses the same dialog as every forward day.

## 5. Next Off Roster behaviour

Home scans the locally derived roster forward for the next Off Roster day. Consecutive OR days are grouped and expressed naturally as a date range with a day count. A single day is labelled as one Off Roster day. The scan does not infer annual leave or generic rest semantics.

The implementation respects actual-day overrides: an actual worked record over a rostered OR is not advertised as the next time off, while an explicitly recorded OR can become the result.

## 6. Four-week forward-view design

The chosen structure is four stacked calendar-week strips:

- current Monday–Sunday calendar week;
- the following three Monday–Sunday weeks;
- real dates;
- sign-on time as the primary work value;
- duty code as secondary context;
- `OR` plus `Off Roster` text for off-roster cells;
- an `ACTUAL` text marker when an explicit actual record wins;
- one button per day with a complete accessible description.

Two week panels share a row on wider screens; phone uses one week panel per row. The current date has both a visual outline and `aria-current="date"`.

Alternatives considered:

- A single 4 × 7 dense calendar was rejected because it made week headings and touch targets less usable on a phone.
- A horizontally scrolling calendar was rejected because it hid future weeks and made the month pattern harder to scan.
- Full shift descriptions in cells were rejected because they duplicate the full roster and destroy glanceability.
- Pay-fortnight alignment was rejected because the planning question is calendar-based.

The forward map is derived in memory from the existing effective-dated roster engine and actual overrides. It introduces no new storage or network dependency.

## 7. Read-only shift-detail contract

Today, Tomorrow and every forward day open one Phase 1 controlled dialog. A working-day detail contains:

- date;
- duty code;
- combined sign-on/sign-off;
- duration;
- complete locally available shift-book content;
- truthful source label;
- the rostered baseline when a recorded actual differs.

An Off Roster detail contains simply `Off Roster`. Missing shift-book content is described as unavailable rather than invented. The dialog contains no pay settings, Cloud controls, notes field or historical administration.

Opening, closing, tabbing and rotating this dialog are presentation actions. They make zero personal writes, create zero generations and emit zero Cloud writes.

## 8. Today → detail → actual-edit interaction

The former direct Today-to-editor action is now:

`Today` → read-only shift detail → explicit `Edit / record actual day`

The final action closes the detail dialog without returning focus to the old card and opens the existing actual-day editor for the selected date. The editor and its canonical persistence behaviour were not changed. This preserves fast editing while separating the common “what am I rostered for?” task from “what did I actually work?”.

## 9. Terminology changes

- Compact off-roster state: `OR`.
- Full wording: `Off Roster`.
- `Rest` is not used as an OR synonym in the affected Home surfaces.
- The prior `${hours} h recorded` pay summary was replaced with `${hours} h used in this estimate`; those hours can combine roster projections and actual records.
- Current data is described as `Roster projection`, `Saved work pattern`, or `Recorded actual`, using only provenance the application genuinely knows.

Legitimate Rest Job pay terminology elsewhere was deliberately left unchanged.

## 10. Expected-pay treatment

Expected pay now has a distinct, accessible Home button showing:

- expected gross amount when a pay profile exists;
- the pay-period dates;
- the hours used in the estimate;
- concise payslip-check status.

It opens the existing Pay view for calculation detail. Without a pay profile, it says `Set up pay estimate`; no default role or fabricated amount is displayed. Phase 3's contextual pay-setup card remains intact.

## 11. Search hierarchy changes

Search remains available and unchanged functionally, but CSS ordering places it below the daily answers and forward roster. It no longer pushes the most common five-second questions out of the initial hierarchy. The full My Roster card and pay-check utility likewise remain below the planning view.

## 18. Known limitations

- The four-week view is a locally derived projection plus actual overrides; it is not a weekly/daily published assignment.
- Dates beyond supplied frozen roster coverage can truthfully show no roster information.
- A recorded actual is known, but the current data model does not contain the future weekly/daily published-source hierarchy.
- The next-OR answer is only as accurate as the locally available effective roster and actual records.
- At 200% text the calendar becomes vertically tall to preserve readable text and 44 px targets; it deliberately does not shrink typography or add horizontal scrolling.

## 19. Future provenance/change seams

Day rendering now has one internal detail model with a dedicated source/status location. A future release can add a real `Changed`, `Weekly roster`, or `Daily roster confirmed` label without replacing the day cards/dialog structure. No unavailable status is shown today.

The detail dialog also separates the winning day from a rostered baseline. That is a safe future seam for change-awareness while remaining useful now for actual-versus-rostered differences.

## 20. Recommendation for Phase 5

Phase 5 may begin after human beta review. It should focus on understandable Data & Sync, backup, optional Cloud and trust language without disturbing this Home hierarchy or changing schema-5/Cloud architecture. Preserve the daily glance, shared read-only day detail, forward calendar, truthful unconfigured-pay state and lower-priority search treatment.

The Phase 0 questions now have direct answers:

- Today: zero interactions.
- Tomorrow: zero interactions.
- Next Off Roster: zero interactions.
- Next four calendar weeks: visible at a glance, with one tap for detail.
- Inspect a shift without editing: yes.
- Pay configured or missing: explicit and truthful.
- Internal RosterBot structure required: no.
