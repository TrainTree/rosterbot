# RosterBot v0.31.0 Phase 7 release-candidate record

This record freezes and audits v0.31.0 for review before any production rollout. Production deployment, capability, user data and tags are explicitly outside Phase 7.

## Release scope

v0.31.0 adds the installable RosterBot PWA, a hash-verified offline shell, cold offline launch, local editing while offline, safe Cloud reconnection, user-controlled coherent application updates, the approved RosterBot app icon, and the iPhone/iPad standalone refinements proven during Phase 6. It preserves the v0.30 schema-5 persistence, encryption, migration, recovery and server contracts.

The exact source commit, production-bundle build ID, service-worker identity, checksum-tree identity and test totals are recorded after the source is frozen. The authoritative inventory remains `scripts/runtime-assets.mjs`; the manifest, service worker, production/staging generators and checksum audit all consume that inventory.

## Canonical origin and existing shortcuts

`https://rosterbot.work` is the sole production PWA and storage origin. The early bootstrap redirects only `https://www.rosterbot.work` to the apex before application scripts, persistence or worker registration. Beta and localhost remain distinct supported contexts.

A hosting-level permanent `www` → apex redirect is still recommended before v0.31 rollout, so canonicalization normally occurs before application HTML is served. It must preserve path and query. DNS/Pages is not changed in Phase 7.

An existing apex Safari bookmark or pre-manifest Home Screen web clip continues to open the same origin. Its first online v0.31 launch performs normal startup, then registers and installs the worker; later launches can use the verified offline shell. iOS may retain an old web-clip icon/title until the shortcut is deliberately re-added, but that presentation limitation does not fork storage or affect application correctness. An old shortcut targeting `www` is redirected before RosterBot state starts; browser same-origin rules mean any historical local-only `www` storage cannot be read from the apex and must never be assumed migrated automatically.

## v0.30 → v0.31 first-worker contract

The production transition begins with a v0.30 page that has localStorage and IndexedDB personal state but no RosterBot worker or Cache Storage. v0.31 loads directly from the network and completes the existing build-coherence and persistence startup before worker registration. The installing worker cannot control the already-loaded page. It fetches and hashes the complete offline-required set in a new build cache, writes the complete marker last, activates under normal browser lifecycle rules, and claims only after its own complete-cache verification.

Installing or activating the worker never reads personal localStorage/IndexedDB. It therefore cannot advance schema-5 generation, alter an envelope fingerprint, clear an encryption context or cause a Cloud write. Reload is served from one complete v0.31 cache and is independently checked by the Phase 1 build gate. A failed first install deletes only its incomplete cache and leaves the online application and personal state untouched.

The Phase 7 browser rehearsal uses the actual `v0.30.0` tag, realistic migrated schema-5 local state, no pre-existing worker/cache, and both plaintext and remembered-key encrypted Cloud configuration. It requires byte-identical localStorage and IndexedDB envelopes, identical generation and fingerprints, zero Cloud writes, a valid complete marker, coherent reload, browser close/reopen and cold offline startup.

## Release and Cloud invariants

- capability remains 4..5; no Phase 7 step changes it;
- every new Cloud grant still needs a fresh authenticated, exact-project `rosterbot-schema5-cloud-v1` attestation;
- unchanged local/remote state emits no write; genuine changes use one revision-checked save;
- conflicts and RB003 protect remote state; schema downgrade remains rejected;
- encrypted reconnect requires the verified in-memory context, while same-user token refresh does not spuriously lock it;
- application update state, service-worker state and connectivity state stay outside canonical personal state;
- no Auth, REST/RPC, roster/history, encrypted payload, calendar-feed, Formspree or cross-origin response enters Cache Storage.

## Production package audit

The production generator must run from the clean frozen commit into an empty directory. It must prove one production publishable credential; exact apex origin and `rithmbggiiusrmdcqrif` binding; saved configuration and fallback disabled; no staging ref, URL, origin or key; no JWT, PAT, secret/service-role/database credential; runtime-only contents; coherent manifest/worker IDs; and one SHA-256 entry for every deployed file. No bundle is deployed in Phase 7.

## Rollback and fix-forward

Once v0.31 has registered a worker, redeploying the pre-worker v0.30 site is not a reliable browser rollback: an active v0.31 worker may continue serving its complete cache and a forced cache deletion could strand offline users. The preferred recovery is a reviewed v0.31.x fix-forward build with a new identity and complete cache. It installs alongside the known-good build, waits, and activates through the same controlled protocol.

If Cloud safety is implicated, server capability can be held independently at 4..4 while the v0.31 application remains deployed and fully local-first. Do not deploy v0.30 after schema-5 local use, delete user caches remotely, clear localStorage/IndexedDB, unregister workers blindly, mutate envelopes, or bypass attestation/revision guards.

The worker retains the active build and previous complete known-good build. A failed new install cannot activate. If a newly activated document fails before application-ready, personal state remains untouched and the previous complete cache is retained as recovery evidence. Where browser lifecycle rules prevent automatic controller rollback, publish a coherent fix-forward worker and present the distinct application-update failure state; never route an asset failure into Data Recovery.

## Phase 8 production sequence

1. Reconfirm the frozen commit, clean tree, bundle checksums, production identity/capability/Auth/catalog and live v0.30 asset hashes.
2. Add/verify the hosting-level permanent `www` → apex redirect without serving a second app origin.
3. Deploy the exact reviewed v0.31 bundle while capability remains 4..5; do not mutate Cloud state as part of deployment.
4. Verify every hosted byte, manifest identity, worker identity, canonical redirect and normal online startup.
5. Exercise the no-worker → complete-worker transition in a controlled production browser, confirming generation/revision do not move.
6. Verify cold offline launch, reconnect, encrypted owner flow and one harmless canonical edit under the existing capability contract.
7. If any data-integrity/security gate fails, hold Cloud at 4..4, leave the coherent v0.31 client deployed, preserve evidence and fix forward.
8. Tag the exact deployed source as `v0.31.0` only after the production rollout passes.
