# RosterBot v0.32 Phase 1 — Persistence Trust Boundaries & Accessible Dialog Foundation

## Outcome

Phase 1 removes the restart-visible canonical write gap found in the blind audit and establishes one reusable modal/focus-management contract. Safe Data Recovery remains fail closed. Schema 5, the Cloud payload and server contracts, encryption, migration semantics, and service-worker/update semantics are unchanged.

One accepted initial setup now advances the canonical state exactly once. A draft setup change advances it zero times. At a restart-observable boundary, the browser exposes either the prior verified generation or a fully verified successor; it no longer exposes a newly written compatibility value beside an older schema-5 envelope.

## 1. Affected write-path map

The defect was broader than one onboarding field. The relevant paths were:

- Initial-setup controls called `saveRosterSession()`, which wrote `rosterbot-session-settings-v1` directly and then called `notifyPersonalChange()`.
- The old `notifyPersonalChange()` retained the already-visible value, waited 40 ms, and later regenerated the schema-5 envelope/projection.
- `saveCurrentAsMyRoster()` separately created the timeline, employment entry, leave state, session state, manual pattern, and experience/navigation state. Those setters could independently request projection work.
- The success route then moved to the current pay cycle and wrote session view fields again, which could create a second generation.
- Diary, roster-history, fortnight-note, pay-check, employment, PayBot, calendar-setting, roster-view, and configured-session handlers followed the same general direct-write-then-notify pattern.
- `mirrorNow()` and its timer, `pagehide`, and hidden-page lifecycle calls could copy canonical compatibility values to IndexedDB independently of the schema-5 generation transaction.
- Projection synchronisation built the next state from live compatibility storage. It did not have a durable intent record for an interrupted ordinary personal edit.
- A roster preview dispatched `rosterbot:forecast`; PayBot could persist derived forecast state during this render-only path.

The schema-5 envelope, checksum/fingerprint, ancestry, compatibility projection, guard, marker, and IndexedDB mirror are produced by the migration/persistence layer. Those are now the sole authoritative path for committing canonical personal changes.

## 2. Draft versus canonical policy

Unaccepted first-run setup is classified as a device-local draft in `rosterbot-setup-draft-v1`.

- It is resumable after refresh, backgrounding, close, and reopen.
- It is excluded from canonical schema-5 state, generation fingerprints, backups, Cloud, and the personal IndexedDB surface.
- It never represents an accepted roster and never advances a generation.
- It is deleted only after the accepted canonical transaction verifies.

Once a timeline exists, the same session settings retain their established schema-5 classification. This phase does not reclassify the existing session-settings contract.

Abrupt process termination can theoretically lose a browser event that was never dispatched, but any draft value that reached `localStorage` is resumable. Loss or delay of a draft event cannot damage committed personal state.

## 3. Canonical transaction design

`RosterBotSchema5Persistence.commitPersonalChanges()` accepts a complete change set rather than relying on compatibility storage to become authoritative first.

The transaction:

1. reads and verifies the current schema-5 envelope from localStorage and IndexedDB;
2. overlays the requested personal-key changes in memory;
3. validates and fingerprints the complete candidate;
4. returns a semantic no-op when its projection fingerprint is unchanged;
5. creates one successor envelope with one predecessor;
6. writes a small `rosterbot-schema5-personal-commit-v1` intent journal before changing any canonical surface;
7. writes and verifies the envelope in both stores;
8. writes and verifies the exact compatibility projection in both stores;
9. writes the guard and schema marker;
10. performs final envelope/projection verification; and
11. removes the intent journal last.

Startup resumes a valid prepared intent before the ordinary schema-5 verification gate. A fault before the journal leaves the old state untouched. A fault after the journal either rolls the attempted surface back immediately or leaves enough verified intent to finish the exact prepared generation at restart. Malformed intent evidence fails closed.

For legacy individual setters, `notifyPersonalChange()` now captures the requested value and immediately restores the last committed compatibility value. The requested value is then passed to the same transaction path without a timer. Thus a synchronous kill cannot leave that requested compatibility value exposed beside the old envelope.

Cloud observation is suppressed only while the local replacement is in progress, using the exact begin/end token pair, and receives one notification only after a changed generation verifies.

The diary compatibility mirror no longer writes canonical personal keys. Lifecycle mirroring is retained only for non-personal device/derived values.

## 4. Confirmation generation behaviour

Before Phase 1, one confirmation could expose several direct writes and then create a later session/navigation generation. The blind audit also demonstrated the earlier compatibility value plus older envelope boundary.

After Phase 1:

- fresh migration baseline: generation 1;
- one **Use this as my roster** decision: generation 1 → 2;
- emitted generation events: exactly one, reason `accept-initial-roster`;
- timeline entries: one;
- initial employment entries: one;
- draft removed only after verification;
- dashboard transition: no additional generation;
- semantically unchanged acceptance/sync: no generation.

The accepted session includes the current pay-fortnight view used by the success route, so navigation no longer materialises a second session-settings change.

## 5. Abrupt close and background results

Chromium restart tests exercised approximately 0, 5, 10, 25, 40, 75, and 200 ms boundaries.

Draft field change:

- 7/7 resumed the selected draft value;
- canonical generation remained 1 in every case;
- no case entered Data Recovery.

Confirmation with deliberately delayed IndexedDB:

- the immediate boundary, and occasionally the 5 ms boundary before intent became durable, retained the complete old generation 1;
- boundaries after durable intent completed or resumed the complete new generation 2;
- no hybrid timeline/session result occurred;
- the intent journal was absent after successful restart;
- no case entered Data Recovery.

Configured-user session navigation:

- every restart produced either the complete prior generation 2 or the complete successor generation 3;
- the corresponding session value matched the winning generation;
- no case entered Data Recovery.

## 6. Delayed and faulted storage results

- A delayed IndexedDB write left the prior compatibility value visible until the successor verified.
- Interruptions after intent, after envelope, after projection, and immediately before final verification resumed to one verified successor.
- Invalid input rejected before an intent journal and preserved the prior envelope/projection byte-for-byte.
- A synthetic IndexedDB fault after the local envelope surface had been attempted rolled that surface back, retained the prepared intent, and completed exactly one successor after the fault was removed.
- Existing schema-4 migration interruption, quota, unavailable-IDB, read-back mismatch, replacement rollback, and recovery matrices remain green.

Genuine unverifiable storage faults still enter the existing recovery system. No recovery check was weakened.

## 7. Additional hazards found

Two additional Phase-1 integration hazards were found and corrected:

- A render-only `rosterbot:forecast` event could cause PayBot to persist during onboarding preview. It now refreshes the preview with `persist: false`; genuine PayBot edits remain canonical.
- The first implementation paired Cloud `beginReplacement()` with a tokenless release, leaving automatic reconciliation suppressed. The exact returned token is now passed to `endReplacement()`. The full offline/reconnect matrix proves suppression is released, capability attestation is refreshed, conflicts remain protected, and encrypted reconnect still works.

The Phase-4 browser harness also now closes Data & Sync through its normal Close control before attempting a background app edit. This reflects the new correct inert/modal behaviour rather than bypassing it.

## 10. Dialog-controller design

`js/32-dialog-controller.js` is a build-coherent feature module and provides one topmost-dialog stack.

For each controlled dialog it:

- records the invoker;
- ensures `role="dialog"`, `aria-modal="true"`, and a programmatically focusable dialog shell;
- selects a requested initial target or the first current focusable control;
- moves focus after opening;
- recomputes focusable controls for each Tab action, excluding hidden, disabled, and inert controls;
- wraps Tab and Shift+Tab;
- contains stray programmatic/background focus;
- marks background body branches `inert` and `aria-hidden`, restoring their prior values exactly;
- routes Escape and allowed backdrop actions through the feature's existing close callback;
- supports a topmost stack for nested tasks; and
- restores the invoker, or a deterministic application fallback when the invoker disappeared.

It does not read or write persistence, resize overlays, or participate in VisualViewport handling.

## 15. Remaining known risks

- Browser automation models page close and persistent-profile restart, including very short timing boundaries, but cannot literally reproduce every operating-system process kill or iOS memory eviction. The durable-intent design does not rely on lifecycle delivery, which is the relevant integrity property.
- A keystroke or selection that the browser never dispatches before an OS kill cannot be persisted; this is limited to device-local draft loss and cannot create canonical inconsistency.
- Real-device VoiceOver/TalkBack announcements and WebKit focus behaviour should receive manual coverage in the later full accessibility phase. The DOM focus/inert contracts are automated here.
- Safe Data Recovery intentionally remains outside the ordinary dismissible-dialog controller and will need its own focused screen-reader review later.
- Session settings retain their existing canonical/Cloud classification. Any future ownership redesign remains explicitly out of scope.

## Recommendation

Phase 2 may begin. The two Phase-0 trust blockers are addressed without changing schema or Cloud contracts: canonical acceptance is restart-safe and single-generation, and the application's visual modals now behave as contained keyboard/accessibility tasks.
