# v0.32 Phase 7 — Published Roster, Provenance & Change-Awareness UX Research

## 1. Baseline

Phase 7 started from clean branch `experiment/v0.32-ux-adoption` at source commit `a3713168875a14a7c0b0fe2ed47e974a45be4cfe`. Production was not accessed or modified.

The implementation is deliberately research-only. It lives at a direct beta-only path, is copied only by the staging bundle generator, is absent from ordinary navigation, the authoritative runtime inventory, the service-worker cache, and the production bundle, and loads no RosterBot persistence or Cloud modules.

## 2. Source hierarchy

The proposed user-facing authority order is:

1. **Master projection** — the long-range baseline.
2. **Weekly roster** — the published assignment for the week.
3. **Daily roster** — the latest published assignment before the work occurs.
4. **Recorded actual** — what the driver records as having happened and the winner for diary/pay.

Later evidence wins the normal display without deleting earlier evidence. A published assignment is not proof of actual work. No real RosterBot data is labelled Weekly or Daily by this phase; those labels exist only inside the synthetic research surface.

## 3. Winning-duty model

Every day presents one winning duty. The research evaluator orders immutable synthetic evidence by source authority and returns:

- one `winner` for normal display;
- the latest non-Actual `published` duty;
- the complete ordered evidence list;
- only material transitions between sources;
- whether Actual differs from published evidence.

The everyday card leads with the duty, time and useful shift contents. Its source is quiet secondary evidence. Users do not reconcile four competing duty cards.

## 4. Meaningful-change definition

The research comparison classifies fields independently of publication arrival:

| Difference | Proposed treatment |
| --- | --- |
| Work ↔ OR or work ↔ leave | Critical planning change; prominent Home/card marker and notification candidate |
| Duty code, sign-on or booking location | Prominent change; concise old → new context |
| Sign-off only | Quiet detail-level change unless operational research later proves higher urgency |
| Shift contents only | Detail-level evidence; normally no Home alarm |
| PH state | Meaningful status evidence, but not automatically a changed-duty alarm |
| Same semantic duty from a newer source | No change marker or acknowledgement |

Whitespace, formatting, publication identifiers and receipt timestamps are not duty changes. The eventual production comparison rules will need domain review for location and contents; this phase does not create a production rules engine.

## 5. Home treatment

The accepted Home hierarchy remains unchanged. The prototype reuses the existing Today and forward-roster visual primitives to test only the additional information:

- show the winning duty as the normal card;
- retain a quiet source line;
- add one readable change sentence only when the winning duty materially differs;
- for Actual, say **Recorded actual** and prioritise it;
- when Actual differs, state that it differs from the published duty without treating the publication as reality.

An unchanged weekly or daily publication produces no banner. The source quietly becomes more authoritative.

## 6. Four-week calendar treatment

The proposed calendar treatment is deliberately restrained:

- normal cells retain the current work/OR/ALR/PH language;
- one materially changed day gains a visible border plus the word **CHANGED**;
- a recorded Actual uses **ACTUAL**;
- a changed Actual can say **ACTUAL · CHANGED**;
- accessible names include the same state in words;
- tapping the day opens the same evidence detail as the winning-duty card.

This avoids stacking source badges into every compact cell. Month boundaries, OR, leave, PH and current-day treatments remain conceptually separate.

## 7. Day-detail provenance treatment

Day detail is the primary provenance surface. Its proposed hierarchy is:

1. source and **Current duty**;
2. **Changed from** only when the winning source materially changed the duty;
3. **Published duty** when a recorded Actual differs;
4. shift contents;
5. collapsed **Duty history** with all evidence.

The full Master → Weekly → Daily → Actual chain is therefore available without appearing on every ordinary day. Projection-only days hide unnecessary history controls.

## 8. Actual versus published behaviour

Actual always wins for diary/pay. If it matches the latest published duty, the presentation remains calm and simply identifies it as Recorded actual. If it differs:

- Actual is the current duty;
- the latest published duty is separately labelled and retained;
- detail explains that the Actual is used for diary/pay;
- later weekly/daily evidence must never overwrite the Actual.

This explicitly avoids the false claim that a daily roster proves what was worked.

## 9. Unchanged-publication behaviour

Weekly-confirmed projection and daily-confirmed weekly fixtures produce:

- no changed marker;
- no acknowledgement action;
- no noisy announcement;
- the same visible duty;
- a newer source label in detail/secondary evidence.

Publication and change are separate concepts. “New weekly roster available” must never mean “your shift changed.”

## 10. Change-marker lifecycle

Recommended lifecycle:

- mark a current/upcoming material change when first received;
- keep critical work/OR changes visible until viewed or the affected day passes;
- allow opening detail to be informative without automatically acknowledging it;
- use an explicit low-friction **Mark change as seen** action where acknowledgement is useful;
- after acknowledgement, reduce the calendar marker to **VIEWED** during the active planning window;
- remove stale Home emphasis after the day, while retaining permanent evidence in Duty history;
- do not sync “seen” state until its device/account semantics are deliberately designed.

The prototype acknowledgement is memory-only and intentionally resets on reload.

## 11. Alarm-fatigue findings

The calmest successful model is event-based rather than source-based:

- seven unchanged weekly assignments create zero warnings;
- repeated daily publications with the same assignment create zero warnings;
- one changed day produces one marker, not a week-wide warning;
- multiple successive changes show only the current winner on Home and the chain in history;
- detail-only sign-off/content adjustments do not compete visually with work/OR or sign-on changes;
- old changes leave the active dashboard but remain auditable.

Permanent red badges, publication-arrived banners, and multiple old/new cards were rejected as unnecessarily forensic and likely to cause alarm fatigue.

## 12. Notification recommendations

No notification infrastructure was built. Recommended future priority:

- **Active/high priority:** `Tomorrow changed: sign-on now 11:00`; `Friday changed from Off Roster to SP456`; work changed to Off Roster.
- **Active/normal:** a duty-code or material sign-on change later in the upcoming planning window.
- **Passive/in-app:** sign-off-only or contents-only correction unless domain research says otherwise.
- **Silent evidence update:** `New weekly roster available — no changes to your duties` should normally remain a quiet sync/status fact, not a push notification.

Notifications should state the outcome first, link to day detail, coalesce repeated corrections to the latest winner, and never expose another employee’s information.

## 13. Search implications

Normal Search should index and return one winning duty per day. Search result names may include the current source or Changed state only where useful. Prior source records should not appear as duplicate normal results; **Duty history** is the evidence route. Advanced evidence search could be considered later for disputes, but should not shape everyday Search.

## 14. Pay implications

No pay calculation changed. Proposed future rule:

- projection provides the initial estimate;
- weekly/daily winning assignments update expected pay when more authoritative;
- Recorded actual ultimately determines diary/pay;
- a later published source cannot overwrite an Actual;
- recalculation should follow the same single winning-duty resolver, not independently merge sources inside PayBot.

Any pay change caused by a source update should be explainable from the day’s evidence history.

## 15. Proposed future evidence/history model

The future architecture needs immutable, authorised evidence records conceptually containing:

- duty date;
- source type (`master`, `weekly`, `daily`, `actual`);
- source publication/version and stable source identifier;
- published and received timestamps;
- duty code, sign-on, sign-off, booking location and complete contents;
- OR/leave/PH state;
- verified driver-identity mapping scoped to only that user;
- superseded/winning relationship or a deterministic resolver input;
- integrity/provenance evidence appropriate to the private ingestion service;
- user Actual stored separately from employer-published evidence;
- acknowledgement state separately classified from roster truth.

Raw multi-employee documents must remain private and separate from the open static application. Per-user authorised extracts should reach the client; the public repository must never become an operational roster store. This is conceptual only—no schema or backend was changed.

## 16. Accessibility findings

The research surface:

- uses one H1 and logical H2/H3 structure;
- keeps chronological native day buttons rather than an ARIA grid;
- expresses Changed, Viewed and Actual in text as well as colour/border;
- gives controls practical 44px targets;
- uses a native modal dialog with deterministic close focus and Escape behaviour;
- keeps evidence behind an accessible `details` disclosure;
- has a restrained live status for scenario selection;
- respects reduced motion;
- reflows at 200% text without horizontal overflow.

Before production design, the marker wording and history reading order still require real iPhone/iPad VoiceOver review.

## 20. Production architecture recommendations

1. Put source ingestion, document retention and employee matching in a private authorised service, separate from the open static client.
2. Deliver only the authenticated user’s minimal per-day evidence to the client.
3. Keep source evidence immutable; compute the winner deterministically.
4. Keep Actual in the existing user-authority domain and make it impossible for official ingestion to overwrite.
5. Make comparison/change events idempotent and semantic, not tied to fetch count.
6. Keep source publication, duty change and notification delivery as separate concepts.
7. Preserve capability/attestation, encrypted Cloud and downgrade protection when a production data model is eventually proposed.
8. Do not put raw wallsheets/daily rosters in the public repository, Cache Storage, or unauthorised browser state.

## 21. Unresolved product questions

- Is every sign-on change notification-worthy, or should very small corrections remain in-app?
- Should sign-off-only changes ever become prominent for fatigue, transport or pay reasons?
- Does opening detail count as acknowledgement, or should **Mark change as seen** remain explicit?
- Should “seen” be device-local or synchronised between the user’s devices?
- How long should upcoming and past change markers remain on Home?
- Which booking-location/content differences are operationally meaningful enough to surface?
- Should an Actual difference itself be called “Changed,” or simply “Recorded actual” with published evidence in detail?
- What organisational language should replace Weekly/Daily if authorised source names differ in practice?
- What exact identity proof and employer authority are acceptable for private per-driver delivery?

These require driver and organisational judgement before production architecture is selected.

## 22. Recommendation for Phase 8

Accept the single-winning-duty model for further human research, but do not implement published-roster persistence yet. Phase 8 should consolidate v0.32 release-candidate quality and decide whether this beta-only research surface remains an evidence artefact or is removed before release packaging. A later dedicated ingestion milestone should begin only after driver review resolves marker priority, acknowledgement semantics and identity/data-authorisation dependencies.
