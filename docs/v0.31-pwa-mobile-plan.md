# RosterBot v0.31 — PWA, Mobile and Offline audit and design

Status: feature-frozen v0.31.0 release candidate preparation. Phases 1–6 are implemented and the Phase 6 mobile/PWA behavior has passed real-device iPhone and iPad validation.

Baseline: tag `v0.30.0`, commit `f56960de45246574db2ff753bca0521827af3338`.

Branch/worktree: `experiment/v0.31-pwa-mobile` at `~/Projects/rosterbot-v0.31-pwa-mobile`.

## 1. Executive recommendation

RosterBot is already a strongly local-first application, but it is not currently a PWA. It has no web app manifest, app-icon set, Apple PWA metadata, service worker, Cache Storage use, install/update UI, or offline app shell. An uncached load therefore requires the network. Once its same-origin scripts have loaded, ordinary roster, diary, PayBot, backup and one-off calendar work is local; Cloud Sync, live calendar publishing, feedback submission and public-document links are optional network features.

The safest v0.31 design is not a generic stale-while-revalidate service worker. RosterBot must ship each application generation as one verified unit:

1. Generate a build-bound release manifest containing every startup asset, its content hash, byte length and build identifier.
2. Publish application assets under immutable content-addressed or build-addressed URLs.
3. Precache and verify the complete shell during service-worker installation. A missing or mismatched asset fails installation and leaves the old active worker/cache untouched.
4. Serve navigation and known shell assets from the active version's verified cache. Never fill one version's shell from an unverified network fallback.
5. Leave a successfully installed update waiting. Show a plain-language update prompt and activate only after local schema-5 persistence is settled and verified.
6. Never cache, queue or replay Auth, capability, roster-state/history, encrypted payload, calendar-feed, feedback, or other user-specific responses.
7. On reconnect, use the canonical local schema-5 state as the pending truth to reconcile. Obtain a fresh authenticated capability attestation, fetch current Cloud state, run the existing comparison/conflict policy, and make at most the intended CAS-protected save. Do not add an offline HTTP write queue.

This retains the v0.30 persistence architecture and adds an application-delivery boundary around it.

## 2. Current-state audit

### 2.1 Application and deployment shape

- The product remains a static GitHub Pages application: `index.html`, one CSS file, 29 JavaScript files, and two frozen JavaScript data packs.
- The production generator copies runtime files only and creates a deploy-bundle `SHA256SUMS.txt`. It audits the production origin/profile, production Supabase binding and credentials. The source-tree checksum file is not consumed by the browser and must not be treated as an update manifest.
- `index.html` directly loads nine foundational scripts. `js/03-persistence-bootstrap.js` then loads 22 entries sequentially: 20 feature scripts and both data packs.
- The entire cold-start dependency graph is approximately 6.62 MB uncompressed and 0.94 MB when each file is gzip-compressed. Cache Storage quota must be planned for decoded response bodies and at least two application generations during an update.
- There is no bundler and no content-hashed runtime naming. The current URLs such as `js/02-schema5.js` and `js/51-cloud-sync.js` are stable across releases. That makes ordinary browser/CDN caching unsafe as a coherence mechanism.

### 2.2 Manifest, icons and install metadata

None currently exists:

- no `<link rel="manifest">` or manifest file;
- no PNG, SVG or ICO application icons;
- no favicon declarations;
- no `apple-touch-icon`;
- no `apple-mobile-web-app-capable`, `apple-mobile-web-app-status-bar-style`, or Apple title metadata;
- no install-prompt handling (`beforeinstallprompt` / `appinstalled`);
- no standalone/display-mode detection.

What does exist:

- `lang="en-AU"`;
- a mobile viewport with `viewport-fit=cover`;
- a fixed `theme-color` of `#111214`;
- system font stacks only, so startup does not depend on a web-font CDN.

### 2.3 Service worker, Cache Storage and offline shell

None currently exists:

- no service-worker registration or worker source;
- no Cache Storage API use;
- no offline navigation fallback;
- no versioned cache names or cache cleanup policy;
- no worker install/activate/update lifecycle;
- no application-update prompt.

Consequently, a cold launch with no HTTP cache and no network cannot load. “Add to Home Screen” may create a bookmark-like launcher on iOS, but it is not backed by an intentionally cached app shell.

### 2.4 Local persistence startup

The existing startup order is a valuable safety boundary and should remain authoritative:

1. Inline boot diagnostics start before external modules.
2. `js/00-error-handler.js` snapshots readable localStorage without writing.
3. Storage compatibility, registry, canonical state, safety, schema-5 validation, recovery UI and migration modules load before features.
4. The bootstrap checks the local schema marker and newer-schema guard before opening IndexedDB.
5. It reads the `RosterBotPersonalDB` `kv` store, reconciles localStorage and IndexedDB, and performs only verified transactional recovery/migration.
6. It establishes schema 5 before loading feature modules.
7. Feature/data scripts load in a fixed order. Projection verification then completes before `rosterbot:application-ready` is emitted.

This sequence means a service worker must deliver the entire foundational set and the later feature set from one build. It must not replace or bypass any schema-5 checks. A shell asset failure is an application-delivery failure, not evidence that personal data is corrupt.

### 2.5 Existing offline and network-loss behavior

Useful foundations already exist:

- roster, diary, PayBot, manual schedules, backup export/import and local calendar export operate from local state and bundled datasets;
- ordinary edits write locally and schema-5 projection changes are committed to localStorage plus IndexedDB independently of Cloud availability;
- Cloud automatic sync catches request failures, reports “Offline · changes saved on this device,” applies a short backoff, and retries on `online`, focus, visibility and polling events;
- local calendar feed publication also reacts to `online` and visibility;
- manual Cloud refresh already says local changes remain saved if Cloud is unavailable;
- no `navigator.onLine` precondition blocks real requests. This is intentional because that signal is only a hint.

Gaps:

- without a service worker the application itself cannot cold-start offline;
- connectivity is not represented as a deliberate shared state machine;
- an automatic-sync catch can label non-deterministic errors “offline” too broadly; authentication, attestation, HTTP, timeout and transport failures need separate presentation and retry policy;
- reconnect schedules work but there is no app-level explanation of offline/reconnecting/held/conflict states;
- there is no explicit guarantee that reconnect reacquires capability before any schema-5 transfer beyond the existing per-page Cloud gate; tests must make that invariant visible;
- feedback failure logs an Error object to the browser console. It does not log the submitted body, but v0.31 should keep diagnostics secret-free.

### 2.6 Version and update detection

- Visible version strings and schema-5 writer metadata identify v0.30.0.
- There is no central application build identity exposed by every module.
- There is no release polling, update detection, waiting-worker UI, cross-tab update coordination or safe-reload handshake.
- `rosterbot:update-required` currently means persisted data is newer than the running reader; it is not an application-release updater.
- The deploy bundle checksum is useful for deployment audit but is not fetched or verified at runtime.
- Foundational boot diagnostics detect missing/failing foundational files, but later feature modules do not publish a common build identity. A mixed set can therefore fail unpredictably rather than being rejected as a release-coherence error.

### 2.7 Browser and navigation assumptions

- The app is a single document. Views are switched through DOM state and root CSS classes, not URL routes.
- `history.replaceState()` is used only to remove Auth callback secrets from the URL.
- External source documents use `target="_blank"` with `noopener noreferrer`.
- Blob URLs plus `<a download>` are used for `.rosterbot` backups, recovery evidence/keys and `.ics` files.
- Backup import uses a hidden file input and the File API.
- No Web Share API integration exists.
- The page assumes DOM availability for all features and loads feature scripts serially after persistence recovery.

### 2.8 Mobile and responsive layout

Existing strengths:

- many primary buttons meet a 44 px minimum target;
- compact roster views and responsive PayBot layouts exist;
- mobile bottom navigation accounts for `safe-area-inset-bottom`;
- general mobile dialogs account for top and bottom safe areas and use `100dvh` where available;
- dialog headers and day-editor actions are sticky and reachable;
- large roster/source tables intentionally scroll horizontally with momentum scrolling;
- time inputs and key PayBot/day-editor inputs use 16 px text to avoid iOS focus zoom;
- specific prior iPhone overflow and modal-reachability defects have dedicated CSS fixes;
- the history gesture checks `prefers-reduced-motion`.

Remaining risks:

- the top-level header does not apply `safe-area-inset-top/left/right`; a standalone translucent status bar could overlap it;
- `body` still uses `min-height:100vh`; several components retain `vh` fallbacks or limits. Dynamic Safari chrome and standalone keyboard resizing need direct testing;
- the fixed bottom navigation does not visibly account for the virtual keyboard or `visualViewport` changes;
- there is no orientation-change or `visualViewport` handling;
- several long dialogs establish their own scroll containers while the body is locked, which can produce iOS scroll trapping or focus-behind-keyboard problems;
- the main full roster table and official roster viewer intentionally need horizontal scrolling; landscape behavior and scroll-position retention are not tested;
- some controls are 38–43 px high, below the preferred 44 px touch target even though major actions are larger;
- `html { color-scheme: dark !important; }` can conflict with the later light theme and native form/status-bar presentation;
- the fixed document `theme-color` does not follow the selected light/dark/theme appearance;
- no standalone-mode CSS class or media query exists;
- Blob downloads, Files import, object-URL lifetime and external links need testing in iOS standalone mode, where “download” may become a preview/share workflow.

### 2.9 Orientation and keyboard behavior

- The app does not lock orientation, which is the correct default.
- No orientation-specific layout or event handler exists.
- No `visualViewport`, `focusin`, or `focusout` logic exists for keyboard occlusion.
- Several scripted `scrollIntoView()` calls may fight iOS keyboard/scroll restoration in nested modal scrollers.
- Form semantics are generally good (`date`, `time`, `number`, `email`, `password`, `search`, `url`, `inputmode` and autocomplete attributes), but standalone-device verification is still required.

### 2.10 Existing capabilities and missing capabilities

| Area | Existing foundation | Missing for v0.31 |
| --- | --- | --- |
| Local use | Schema-5 localStorage/IndexedDB startup, transactional replacement, local roster/diary/pay operation | Verified offline application delivery |
| Mobile | Responsive layouts, compact views, bottom safe area, mobile modal fixes | Install metadata, top/side safe areas, keyboard/orientation/standalone proof |
| Network loss | Local edits continue; Cloud retries and reports a basic offline message | Typed connectivity state, deliberate reconnect sequencing and user-facing recovery states |
| Updates | Deploy-bundle checksums and boot diagnostics | Build identity, immutable assets, complete-cache installation, waiting update and multi-client activation |

| Privacy | Same-origin runtime, local-first state, encrypted optional Cloud and capability gate | Explicit worker bypass/no-store contract and tests proving no personal response is cached |

The official roster periods span FP64 from 1 December 2024 through FP68 from 23 August 2026 onward. Historical periods are needed to render saved diary/history and to reproduce pay results for old dates. They are not disposable “old cache” data.

### 4.2 Offline policy

- Precache both files in the same verified application generation. They are necessary for current roster lookup, historical diary rendering and pay calculations.
- Treat them as immutable release assets identified by content hash. Do not update them in place inside an active cache.
- A new dataset release creates a new application/release manifest and cache generation. Existing personal schema-5 state remains untouched.
- Keep the old complete application cache until the new generation has fully installed and activation is accepted. A failed or partial dataset download must leave the prior generation usable.
- Do not cache only the “current” FP period: saved history and pay checks depend on effective-dated historical data.
- Defer dataset splitting/lazy loading until startup measurements justify it. Splitting now would enlarge the offline completeness and mixed-version state space. If later adopted, every historical shard needed by saved state must be dependency-declared and hash-verified before activation.

## 5. v0.31 offline contract

### 5.1 Installed user with local data

With no network, an installed and fully cached RosterBot must:

- open from the Home Screen into the last activated coherent application release;
- complete the existing schema-5 localStorage/IndexedDB startup and recovery checks;
- make roster, diary, PayBot, effective-dated roster lookup, local calendar generation, import and export available;
- accept ordinary local edits through the existing transactional persistence path;
- never wait for Cloud before declaring the local application ready;
- show Cloud as `Offline — changes saved on this device`, distinct from signed-out, expired-session, attestation-held, conflict and server-error states;
- retain the canonical local generation until an eligible reconciliation is performed online.

An uncached first visit may fail with the browser's normal offline page. RosterBot must not pretend installability/offline readiness before the complete shell has been verified.

### 5.2 Network loss while open

- Local UI and persistence continue normally.
- Network calls become typed transport failures and do not revoke local state or imply corruption.
- An in-flight Cloud write that has no confirmed response is not blindly repeated. On reconnect, fetch current revision and re-analyse before deciding whether any save remains necessary.
- UI state may use `navigator.onLine` as an immediate hint, but actual request outcomes remain authoritative.

### 5.3 Reconnect

Reconnect should be a debounced, single-flight reconciliation trigger:

1. Mark connectivity `reconnecting`.
2. Re-establish/refresh the same authenticated user session if possible.
3. Obtain a fresh authenticated capability attestation for the exact origin/project/contract.
4. Fetch the current Cloud row.
5. Compare it with the verified local canonical envelope and stored base revision.
6. Apply the existing `up-to-date`, `local-only`, `cloud-only`, upgrade or conflict policy.
7. Use expected-revision CAS for any eligible save and stop for user review on conflict.

No schema-5 grant survives logout, account replacement, invalid Auth, origin/profile mismatch or app reload. A network return event is never itself a grant.

### 5.4 Why there should be no offline Cloud-write queue

The canonical schema-5 local envelope already records the durable latest local state and generation. An HTTP queue would add serious risks:

- it would persist authenticated requests, access tokens or encrypted/user payloads in another subsystem;
- queued expected revisions become stale while offline;
- a replay could duplicate a save or bypass the latest conflict/attestation decision;
- it creates a second source of truth beside the canonical local envelope;
- Background Sync support is inconsistent on iOS.

The safer “queue” is simply the verified local generation plus Cloud sync metadata. Reconnect recomputes intent from current local and remote state; it does not replay an old request.

## 6. Service-worker and cache architecture

### 6.1 Release artifacts

The production build should generate:

- a unique build ID derived from the deployed source commit plus the exact asset manifest;
- an application release manifest containing version, build ID, schema reader/writer range, URL, SHA-256, byte size and content type for each shell asset;
- immutable content-addressed URLs, or URLs beneath an immutable `/releases/<build-id>/` directory, for all CSS, JS, data and icon files;
- one service worker whose embedded expected build/manifest digest cannot be combined with another generation;
- a stable, network-readable release pointer used only to discover a newer release, never to supply an active shell piecemeal.

Every foundational and feature module should publish or be associated with the same build ID. Bootstrap must refuse application-ready if a module claims another build. SRI should be used for initial document-loaded scripts/styles where practical; the dynamic loader must apply the generated URL/integrity map and reject missing or mismatched entries.

### 6.2 Installation

- Install into a new cache named with the full build ID, never into the active cache.
- Fetch all declared shell assets with reload/no-cache semantics.
- Require every response to be successful, same-origin, expected type/size, and SHA-256-equal to the release manifest.
- Only let the install event succeed after the whole set verifies.
- Do not call `skipWaiting()` automatically.
- A failed or interrupted install is discarded by the browser; the existing worker and complete cache remain active.

`cache.addAll()` failure is useful but not enough by itself; explicit hash verification protects against a CDN/deployment window returning successful responses from different releases.

### 6.3 Fetch policy

- **Application navigation:** serve the active cache's verified `index.html` for same-origin in-scope navigations. An online check for a newer release happens separately and must not replace the active document response.
- **Known shell assets:** cache-only from the active build by immutable URL. If missing/corrupt, attempt only the exact immutable URL and verify it before use. Never substitute a same-named file from another build.
- **Manifest and icons:** versioned icons may be cache-first; the update pointer and service-worker script are network/no-store discovery resources.
- **Unknown same-origin GET:** network-only by default. Do not grow the cache opportunistically.
- **Non-GET, authenticated, user-specific or cross-origin requests:** network-only pass-through with no cloning, logging, fallback, queueing or cache insertion.
- **Offline shell error:** if no complete active cache exists, return a small non-personal offline/bootstrap error response. State clearly that saved personal data was not inspected or changed.

### 6.4 Activation and cache retention

- A waiting worker announces `update-ready` with old/new version and build IDs.
- The running app shows a persistent, accessible prompt: “A new version of RosterBot is ready” with `Update now` and `Later`.
- `Update now` first settles pending UI edits and calls the existing schema-5 local persistence flush/verification. It does not require Cloud.
- Coordinate all controlled clients. Prefer asking the user to close/reload other RosterBot windows; otherwise broadcast a coordinated reload and require acknowledgements.
- Only then message the waiting worker to activate. Reload exactly once on `controllerchange`.
- Retain the previous complete cache while any old-build client is still open. Delete only RosterBot-owned cache names, never localStorage or IndexedDB.
- Keep at most the active, waiting and immediately previous verified caches, subject to a client-safe cleanup policy.

### 6.5 Strategy comparison

| Strategy | Assessment for RosterBot |
| --- | --- |
| Cache-first stable filenames | Reject. It can combine an old cached module with a new document/module. |
| Stale-while-revalidate shell | Reject. It deliberately permits mixed generations and silent mid-session change. |
| Network-first navigation plus cached scripts | Reject as the main policy. A new document can run against the old module cache. |
| Precache stable URLs without hashes | Insufficient. A deployment/CDN transition can populate one cache with mixed successful responses. |
| Immediate `skipWaiting()` | Reject. Existing tabs can continue old code while future fetches are controlled by a new worker. |
| Immutable assets + complete verified precache + waiting activation | Recommended. It gives the strongest practical generation coherence while preserving the working prior release. |

## 7. Resources that must not be cached

The service worker must explicitly bypass all of the following:

- Supabase `/auth/v1/**` requests and responses;
- Supabase `/rest/v1/**` requests, including capability attestation, `roster_state`, `roster_revisions`, `save_roster_state` and calendar-feed management;
- all Cloud current-state/history responses, plaintext or encrypted;
- all capability-attestation responses;
- encrypted payload/ciphertext responses;
- public or authenticated calendar-feed responses;
- Formspree feedback requests/responses;
- password-recovery callbacks and URL fragments;
- any request carrying `Authorization`, any non-GET request, and any future user-specific remote response;
- external public PDF/document navigation.

Client Cloud fetches should additionally use explicit `cache: 'no-store'` where compatible. The worker must not store request headers, bodies, tokens, user IDs, roster/pay content, ciphertext or response diagnostics.

This prevents stale Auth or capability responses from becoming authoritative, avoids ciphertext retention in a second browser store, and ensures CAS/conflict decisions always use a live server response. It also keeps Cache Storage limited to public application code and datasets.

## 8. iPhone and iPad PWA design

### 8.1 Manifest and Apple metadata

Add a same-origin manifest with at least:

- stable app `id`, canonical `start_url` and `/` scope;
- name `RosterBot` and a concise short name;
- `display: standalone` and a conservative display override;
- matching background/theme colours;
- purpose-specific 192 px and 512 px icons for Chromium installability, plus an opaque full-bleed maskable icon (including a 1024 px source/export for current Apple guidance) with an adequate safe zone;
- portrait and landscape-capable orientation (`any`), not a lock;
- no shortcuts that expose personal data in labels.

Add Apple touch icon (180 px), capable/title/status-bar metadata and appropriate favicons. Test whether `default` or `black-translucent` status bar is preferable; do not select translucent until the whole top-level shell handles top/side safe areas. Device-specific startup images are optional and high-maintenance; first prefer a correct icon/background launch appearance, then add tested splash images only if current iOS devices materially benefit.

### 8.2 Standalone layout work

- Add explicit standalone detection using `matchMedia('(display-mode: standalone)')` plus `navigator.standalone` for iOS, exposed as a non-canonical UI state.
- Apply safe-area padding to top-level header and left/right edges in standalone mode, not just modals/bottom navigation.
- Standardise viewport sizing around `dvh` with tested fallbacks; avoid relying on `100vh` where keyboard/browser chrome changes matter.
- Test fixed bottom navigation against the home indicator, keyboard and landscape. Hide or reposition it while an input is keyboard-occluded if necessary.
- Audit nested modal/body scroll ownership, scroll chaining and focus restoration.
- Preserve 16 px input text and raise undersized interactive targets to 44 px where practical.
- Make theme/status-bar colour update together and remove the forced-dark colour-scheme inconsistency.
- Preserve orientation rather than forcing it; ensure roster tables retain meaningful scroll position across rotation.

### 8.3 Files, downloads and external links

- Verify `.rosterbot` import from Files in Safari and standalone mode.
- Verify backup, recovery-key/evidence and `.ics` exports. On iOS, feature-detect `navigator.share({files})` as an optional user-invoked path while retaining download fallback.
- Never auto-share or send exported data. Warn that manual backups are plaintext, as v0.30 already does.
- Ensure object URLs remain alive long enough for iOS to hand off the file.
- External links should remain explicit and open outside the app without exposing an authenticated app view.

## 9. Android and desktop installability

Use the standards-based manifest/service-worker path as the primary implementation. Chromium on Android/desktop should receive normal installability and the same update prompt. Desktop Firefox should still receive offline service-worker behavior where supported even though it does not present the same installed-app UX. Platform-specific code should be limited to:

- iOS standalone detection fallback;
- safe-area/viewport fixes proven necessary on WebKit;
- feature-detected file sharing/install UI.

Do not fork persistence, Cloud or cache logic by platform.

## 10. Privacy and security requirements

- Cache Storage contains public executable/static assets only.
- The service worker has no analytics, trackers, external SDKs or personal-data logging.
- No Auth token, recovery URL, key material, roster/pay data, Cloud payload or ciphertext is persisted by the worker.
- The worker never synthesises a successful Cloud/Auth/attestation response.
- Schema-5 capability remains an in-page, fresh authenticated grant. It is reacquired after every app reload/update/new session.
- Existing encrypted Cloud unlock, actual-user binding, downgrade protection, expected-revision saves and transactional local replacement remain unchanged.
- The service worker never writes localStorage/IndexedDB and never clears application storage during cache cleanup.
- Build and cache diagnostics may include only version/build ID, public asset URL/hash, cache state and secret-free error class.
- Content Security Policy should be evaluated once dynamic loading is represented by a generated exact allowlist. Do not add a policy that breaks recovery or blob downloads without dedicated tests.
- Continue using fully same-origin application resources; no web-font, icon or PWA helper CDN is necessary.

## 11. Update lifecycle

### 11.1 User experience

Use an explicit prompt rather than silent immediate activation:

> A new version of RosterBot is ready
>
> Your saved roster is safe. Update when convenient.
>
> **Update now** · Later

If another tab/window is open, say so plainly and ask the user to close it or allow RosterBot to reload all open windows. An update should never appear as a data-recovery warning.

### 11.2 Safety sequence

1. Discover and completely install/verify the new worker/cache in the background.
2. Leave it waiting; continue serving the old coherent version.
3. On `Update now`, disable repeated clicks and show progress.
4. Settle debounced controls and run `RosterBotSchema5Persistence.syncNow('application-update-checkpoint')`.
5. Verify localStorage/IndexedDB canonical agreement. If this fails, keep the old worker active and show the existing safe recovery path.
6. Pause new UI mutations for the brief activation window; Cloud completion is not required.
7. Coordinate clients, activate the waiting worker, and reload once on controller change.
8. New page boots from the new complete cache and runs the normal schema-5 startup checks.
9. Reacquire any Cloud capability through a fresh attestation.

“Later” keeps the current worker/cache active. Closing all windows may permit a waiting worker to activate only if the product has deliberately chosen that policy; explicit consent remains preferable for low-confidence users.

### 11.3 v0.30 to v0.31 transition

v0.30 has no RosterBot service worker. The first online v0.31 load registers the worker only after a normal safe startup and then installs the complete cache. Do not claim offline readiness until install verification completes. Existing v0.30 tabs remain in memory until closed/reloaded and continue to be protected by server-side schema/revision/downgrade rules.

## 12. Testing strategy

Every phase must continue to run the complete v0.30 persistence, migration, fault, Cloud-client, server-contract, backup/import and browser suites. PWA tests are additive.

### 12.1 Automated release and worker contract tests

- generated release manifest contains every cold-start asset exactly once;
- every declared hash/size matches the production candidate;
- every HTML/bootstrap asset reference is immutable and belongs to the same build;
- no undeclared runtime module can load before application-ready;
- all modules/data publish or resolve to the expected build ID;
- service-worker routing caches only the exact same-origin public allowlist;
- Auth, REST/RPC, attestation, state/history, encrypted, calendar, feedback, cross-origin, authenticated and non-GET requests are never cached;
- cache cleanup can delete only names under the RosterBot application-cache prefix;
- production bundle audit still rejects staging identifiers, secrets and test content.

### 12.2 Automated browser matrix

Using an HTTPS/localhost test server capable of switching between two release trees:

1. first online visit installs but does not disturb current local state;
2. subsequent cold launch, reload and close/reopen work fully offline;
3. local roster/diary/note/pay edit offline creates exactly one intended schema-5 generation and matching IndexedDB copy;
4. Cloud UI reports offline without auth-loss/corruption semantics;
5. reconnect obtains a fresh capability attestation before state/history/save transfer;
6. reconnect with unchanged remote makes at most one intended save and no duplicate;

## 14. Risks and open questions

1. **Canonical origin:** `rosterbot.work` and `www.rosterbot.work` are distinct storage and service-worker origins. Serving/installing on both can create two local-data islands. Prefer an HTTP redirect from `www` to the apex before service-worker registration, but first confirm whether any real local data currently exists under `www` and design a safe migration notice if needed.
2. **GitHub Pages deployment/CDN behavior:** content-addressed URLs plus hash verification are still required even if Pages deployments appear atomic. Confirm cache headers for the worker, release pointer and immutable assets in beta.
3. **Large eager datasets:** caching fixes transfer/offline availability, not JavaScript parse/memory cost. Measure on older iPhones before considering code/data format changes.
4. **Cache quota and eviction:** keep only a bounded number of complete builds and request persistent storage through the existing UI where supported. iOS may still evict data; exported backup/Cloud recovery remain necessary.
5. **Multi-window activation:** define whether `Update now` reloads all clients or requires the user to close others. Never activate into an uncoordinated old tab if stable asset URLs remain.
6. **iOS download/share behavior:** current Blob/download flows need real-device proof and may need a feature-detected Share Sheet path.
7. **Status bar/theme:** choose a tested Apple status-bar style only after top safe areas and dynamic theme metadata work.
8. **Light-theme native controls:** resolve the forced dark `color-scheme` rule without changing theme semantics.
9. **Offline authentication wording:** a transport failure must not sign out the user or clear a valid same-user crypto context. A genuine refresh rejection may do so under the existing rules.
10. **Calendar publication on reconnect:** it is a separate remote projection and must not race or be mistaken for canonical roster Cloud Sync.
11. **Source checksum drift:** replace the stale/non-runtime role of the repository-root `SHA256SUMS.txt` with generated release evidence or clearly document it; runtime verification must use the candidate's generated manifest.
12. **Scope control:** no persistence schema or Cloud contract change is indicated by this audit. Any discovered need for one must stop and receive separate review.

## 16. Phase 1 implementation record — build coherence and canonical origin

Phase 1 implements the build-coherence foundation without a web app manifest, service worker, Cache Storage, fetch interception or update prompt.

### 16.1 Canonical production origin

`https://rosterbot.work` is the only canonical production application and future PWA origin. `https://www.rosterbot.work` remains a supported entry alias, but it must not initialize a second persistence, Cloud or service-worker island.

The early `js/00-canonical-origin.js` decision runs in the document head before `js/00-error-handler.js` takes the startup storage snapshot. It redirects only the exact HTTPS `www.rosterbot.work` origin with `location.replace()`, preserving path, query and fragment. While that navigation is pending, the storage probe is skipped and the persistence bootstrap returns before opening localStorage or IndexedDB. The production Cloud deployment profile now accepts only the apex origin, providing a second fail-closed boundary if navigation is blocked. Beta, localhost, loopback and other test/development origins continue without redirection.

Production DNS/Pages configuration is unchanged in this phase. Before v0.31 production release, the hosting layer should add a permanent HTTP redirect from the `www` alias to the apex so canonicalization normally occurs before HTML is downloaded. The client decision remains defense in depth. Release planning must also consider whether any existing browser has local-only data under the old `www` origin; the two origins cannot directly read one another's storage.

### 16.2 Authoritative runtime inventory

`scripts/runtime-assets.mjs` is the single ordered source of truth for:

- the document and stylesheet;
- generated build identity;
- foundational scripts in startup order;
- dynamically loaded feature scripts and frozen roster/pay datasets;
- the complete cold-start asset set;
- generated manifest and deployment-support filenames.

Both production and staging Pages generators copy this inventory rather than scanning `css/`, `data/` and `js/` independently. The schema-5 bootstrap obtains its dynamic feature order from the generated identity instead of retaining another handwritten array. Tests compare the inventory with every current runtime file and reject duplicates, omissions, extra runtime files, or a deployment generator that reintroduces a separate directory list. Phase 2 manifest/icon assets will be added to this same inventory.

### 16.3 Generated build identity and manifest

`npm run build:identity` deterministically normalizes the build-stamp field, hashes every source runtime input together with the exact source commit when available, and derives an immutable `rb-build:<sha256>` identifier. It then emits:

- `js/00-build-identity.js`, the cheap startup contract;
- `rosterbot-build-manifest.json`, containing application version, build ID, source commit when built from a clean or explicitly identified commit, manifest format version, cache namespace, complete-build marker, minimum application version, and SHA-256/byte length/content type for every cold-start asset.

The source commit is deliberately `null` for a dirty development worktree rather than claiming that uncommitted bytes came from `HEAD`. A clean deployment worktree records its exact commit, and an exact full commit can be supplied through `ROSTERBOT_SOURCE_COMMIT`. `npm run check:build` fails if the identity, stamps or manifest are stale. The generated JSON manifest is installation metadata, not an additional cold-start dependency, avoiding a self-hash cycle while still hashing every file needed to start the application.

The future cache namespace is `rosterbot-app-<build-hash>`. A complete installation is represented by `rosterbot-complete-<build-hash>` only after every manifest asset has been fetched and hash-verified. These names are interfaces only in Phase 1; no cache is created yet.

### 16.4 Runtime coherence enforcement

The document declares its expected build ID before any external application script. Every startup JavaScript/data asset carries one generated build stamp and reports it to `RosterBotBuild` before executing its module body. The persistence bootstrap also requires every foundational component to have reported the expected build before it reads or reconciles personal state.

An absent identity, absent foundation, mismatched document or mismatched component throws `ROSTERBOT_BUILD_MISMATCH` (or the missing-identity equivalent). Boot diagnostics show a distinct **RosterBot application files do not match** message containing only expected build ID, observed build ID, component and reason. It does not enter Data Recovery and does not read, write, clear or repair personal state. Normal startup, schema-5 reconciliation and feature order are otherwise unchanged.

This is a low-cost in-memory comparison; it adds no startup hash downloads. The complete generated manifest remains the byte-level authority for deployment audits and the future service worker.

### 16.5 Contract for the later service-worker phase

The atomic-cache implementation must consume `rosterbot-build-manifest.json` directly. During install it will create only the manifest's cache namespace, fetch the exact listed URLs, verify response status/type/size/hash, and write the complete-build marker last. It must not activate or serve a cache without that marker. The worker's embedded expected manifest/build identity and the page's runtime component checks provide separate installation-time and execution-time defenses.

Production and beta generators may apply different deployment profiles; each resulting byte set therefore receives its own deterministic build ID and manifest. A service worker must never infer an inventory by walking directories or maintain another precache list.

## 19. Phase 3 implementation record — atomic app shell and offline caching

Phase 3 introduces the first service worker without changing schema-5 persistence, Cloud payloads, migration, recovery, or reconciliation. The service worker is a generated release artifact, not a hand-maintained runtime source file.

### 19.1 Exact-build worker and offline-required set

`scripts/service-worker-build.mjs` consumes the generated format-2 `rosterbot-build-manifest.json` and emits `service-worker.js`. The worker embeds the exact application version, build ID, manifest format, cache namespace, complete-build marker and SHA-256/byte-length records for its assets. Production and staging bundle generators invoke the same generator after applying their deployment-specific runtime profile, so each deployed byte set receives its own worker and build identity.

The authoritative inventory currently contains 46 runtime assets:

- 35 `startup-critical` assets: the document, CSS, build/coherence foundation, application modules and frozen roster/pay datasets;
- 8 `installability-critical` assets: display/worker-registration modules, manifest, app/maskable icons and Apple touch icon;
- 3 cosmetic favicon resources.

The deterministic offline-required set is the union of startup-critical and installability-critical assets: 43 files. Cosmetic favicons are fetched and validated best-effort. `service-worker.js` is generated from the manifest rather than listing itself, avoiding a self-hash cycle; deployment tooling adds the verified generated worker to the bundle and release checksums.

“Complete build” means that every one of the 43 required files has returned a successful, non-opaque response whose byte count and SHA-256 match the embedded manifest, followed by a valid marker in the exact `rosterbot-app-<build-hash>` cache. The marker includes the application/build/manifest/cache identity, offline-set digest and required-file count. A cache without that exact marker is non-runnable regardless of how many files it contains.

### 19.2 Atomic install and failure behavior

Installation validates and writes required files sequentially and writes the complete marker last. Concurrent installers for the same immutable build may write only identical validated bytes; they never delete one another's cache. A failed or interrupted install leaves no complete marker, so the partial cache is explicitly invalid and cannot serve navigation or application assets. A retry deterministically overwrites every required entry with verified bytes before adding the marker. The current complete build is never deleted or modified by a failed newer install, and Cache Storage code has no access to localStorage, personal IndexedDB, recovery markers, crypto state, or Cloud payloads.

Phase 3 deliberately performs no foreign-cache deletion during activation. Browser update checks and multiple clients can overlap in ways that do not provide a safe proof that a foreign cache is unused. Complete old builds and foreign incomplete caches are therefore retained until the coordinated Phase 5 update/retirement protocol can identify safe deletion targets. This is a bounded-lifecycle issue for that later phase, not grounds to risk deleting a working or installing build now.

No worker calls `skipWaiting()`. A successfully installed update remains waiting while an older controlled client exists. Activation first requires the exact complete marker, then claims eligible clients. Registration state is exposed through `window.RosterBotOfflineShell` as unsupported, registering, installing, waiting, active or failed; refresh publication is sequence-safe so overlapping worker events do not publish half-refreshed state. Registration happens only after application-ready and canonical-origin/build-coherence prerequisites. Failure is reported as unavailable offline capability and does not invoke Data Recovery.

### 19.3 Fetch and navigation contract

The worker responds only to same-origin `GET` requests whose path is in its embedded build inventory, plus navigation within its scope. A running build resolves known application assets only from its own complete build cache. Cached bytes are rechecked before use. If a known entry is missing or corrupt, online repair is accepted only when the response exactly matches that same build's hash; bytes from a newer or older build are rejected rather than mixed.

Scoped navigation returns the active build's verified cached `index.html`, preserving the requested path/query in the browser while using the existing static application shell. If the active cache is incomplete or damaged and exact online repair is unavailable, navigation receives a distinct 503 **RosterBot application files are unavailable** shell. It states that personal roster data was not changed and never enters Data Recovery.

All other traffic bypasses the worker and Cache Storage, including:

- every cross-origin request;
- Supabase Auth, REST and RPC requests;
- capability attestation, current Cloud state, history and encrypted payloads;
- calendar/feed publication or retrieval;
- Formspree feedback;
- unknown same-origin/API paths and external links;
- all non-GET requests.

The worker neither reads nor stores authentication headers/tokens or remote response bodies. Network failures for those requests propagate to the existing application runtime. Phase 4 will give those failures an explicit offline/transport state and safe reconnect policy.

### 19.4 First load, cold offline launch and updates

The first uncached visit still requires the network. Once a full build has installed and activated, a closed/reopened browser can navigate offline to the cached document, load all foundational/application modules and frozen datasets, pass the runtime build-coherence gate and start against existing local schema-5 state. Roster calculation, diary APIs, PayBot calculation and normal local persistence remain available without contacting the server.

In the A-to-B browser simulation, B receives its own cache and marker and remains waiting. An A-controlled page continues to receive the complete A document and modules after reload; B does not call `skipWaiting`, take control, mutate personal state or cause a canonical generation. Interrupted/invalid B installation leaves A intact. Final user-authorised activation, multi-tab coordination and safe cache retirement remain Phase 5 work.

### 19.5 Phase 3 verification and Phase 4 boundary

Automated service-worker tests cover successful install, marker-last ordering, concurrent same-build install, required-asset 404/timeout/hash mismatch/interruption, prior incomplete cache repair, activation without foreign-cache deletion, corrupt/mixed response rejection and exact repair, damaged navigation, Cloud/Auth/cross-origin bypass, and non-fatal registration failure with zero personal-state access.

The real Chromium matrix proves online installation, browser-close/reopen cold offline launch, offline reload, unchanged schema-5 state at startup, locally calculated roster/diary/pay availability, an offline UI edit with exactly one intended generation, reload persistence, and a complete waiting B while the open A client remains coherent. It also asserts zero cross-origin requests in the local/offline matrix.

Phase 4 should now add a typed runtime connectivity/Cloud-availability state machine. It should distinguish transport offline from Auth loss, attestation hold, timeout, server rejection and conflict; keep local persistence fully available; perform a fresh authenticated capability attestation before any resumed Cloud operation; reconcile canonical state rather than replaying an HTTP write queue; and give calendar/feedback operations equivalent network-only treatment. It must not change the service worker into a cache for user-specific responses.

## 20. Phase 4 implementation record — offline runtime and safe Cloud reconnection

Phase 4 treats connectivity as non-canonical runtime information. It does not change schema 5, migrations, encrypted payloads, server RPCs, recovery, transactional replacement or service-worker fetch policy. The additional runtime module increases the authoritative inventory to 47 assets, of which 44 are offline-required.

### 20.1 Typed runtime state

`js/08-connectivity-state.js` defines the complete device-runtime vocabulary: `online-eligible`, `offline`, `transport-unreachable`, `timeout`, `unauthenticated`, `auth-lost`, `auth-refreshing`, `attestation-unavailable`, `capability-hold`, `server-rejection`, `revision-conflict`, `encryption-locked`, `encryption-verification-failed`, `disabled`, `syncing`, `synced` and `pending`.

The state contains only safe operational metadata: state, reason, pending flag, bounded retry time and transition time. It is kept in memory, exposes no token, user payload or crypto material, and is not written to localStorage, IndexedDB, schema 5 or Cache Storage. `navigator.onLine` and browser events are hints. A real Cloud response remains authoritative; browser-online plus a failed fetch is `transport-unreachable` or `timeout`, not `synced` or `auth-lost`.

Cloud status uses quiet plain-language outcomes including **Offline — changes saved on this device**, **Back online — checking Cloud…**, **Cloud sync pending**, **Cloud up to date**, **Sign in to sync**, **Unlock Cloud Sync**, and **Cloud sync needs attention**. Normal transport loss never invokes Data Recovery.

### 20.2 Local-first pending work and no HTTP queue

An offline canonical edit follows the unchanged schema-5 transaction path and can create a normal local generation. Cloud auto-sync records only an in-memory pending reason, suppresses requests while the browser is known offline and retains one coalesced timer/reason rather than one item per edit. On reload or browser reopen, the durable pending condition is reconstructed by comparing the verified current canonical fingerprint with the last-synced fingerprint. There is no serialized request body, request journal or HTTP replay queue.

Multiple offline generations therefore collapse into the newest verified canonical envelope. They do not fabricate Cloud revisions. A valid local edit is never rolled back because transport failed, and Cloud status is never reported as synced until canonical comparison or a revision-checked save succeeds.

### 20.3 Reconnect sequence and conflict protection

Offline transition revokes the in-memory schema-5 capability grant but deliberately does not clear a verified encryption context. Noisy `online` events are debounced. Reconnect then:

1. verifies that the browser no longer reports offline;
2. verifies or refreshes the current authenticated session;
3. obtains a fresh authenticated capability attestation;
4. fetches the current remote row and revision;
5. validates/decrypts it where required;
6. compares canonical local, remote and last-synced fingerprints through the existing analysis rules;
7. stops for an existing conflict/recovery choice where required;
8. otherwise emits at most one `save_roster_state` call with the authoritative expected revision.

Transient failures use bounded exponential backoff (10 seconds to 5 minutes) and existing foreground probes; there is no active connectivity endpoint or runaway retry loop. A reconnect with no semantic difference updates no generation and emits no save. Revision `RB003`, a remote change while offline, or two-device divergence retains the existing conflict path and cannot become a blind overwrite.

Capability 4 remains a hard hold: local schema-5 state stays pending and no write occurs. A later capability-5 attempt starts with another fresh attestation and complete remote comparison. Cached app-shell content is never consulted for capability or Cloud decisions.

### 20.4 Encrypted reconnect and authentication

Offline local persistence does not require the Cloud encryption key. A reconnect upload for an encrypted account still requires the verified runtime key consumed by the v0.30 encryption path. Network loss and same-user token refresh preserve that context. Logout, actual auth loss, user change, deployment/config mismatch and explicit lock retain their established revocation behavior. If locked, the canonical local state remains safe and pending until the user unlocks; wrong-key or integrity failures remain distinct from connectivity failures.

### 20.5 Session-settings observation

`rosterbot-session-settings-v1` remains a canonical personal-state object in the schema-5 registry. Phase 4 does not reclassify it. The existing Cloud compatibility normalization and immediate auto-trigger comparison exclude `displayWeeks`, `experienceMode`, `lastViewedFrom` and `lastViewedTo`, but the schema-5 envelope still records changes to those fields and the periodic verified fingerprint probe can subsequently discover them as canonical changes. Under the current contract, offline navigation changes to those fields can legitimately advance a local generation and can eventually produce one coalesced Cloud save on reconnect.

That behavior can create Cloud churn from navigation preferences. It is recorded as a post-v0.31 schema-design question; changing individual field ownership would be a persistence-contract change and is intentionally out of scope here.

### 20.6 Calendar and feedback

Calendar publication and Formspree feedback remain network-only and outside the service worker. Known-offline manual actions explain that the network is required. ## 21. Phase 5 implementation record — controlled PWA update lifecycle

Phase 5 completes the transition from an atomically downloaded waiting worker to a user-confirmed application update. All update state is in-memory page/worker metadata or build-cache metadata. It is excluded from the persistence registry, canonical schema-5 envelopes, generation fingerprints and Cloud payloads.

### 21.1 Typed lifecycle and verified waiting builds

`js/91-update-lifecycle.js` exposes the states `unsupported`, `current`, `checking`, `installing`, `installation-failed`, `complete-update-waiting`, `activation-requested`, `quiescing`, `activating`, `reloading`, `successfully-running-new-build`, `activation-failed` and `recovery-previous-build-available`.

A native `registration.waiting` value is insufficient to show an update. The registration layer queries that exact worker and then independently opens the named Cache Storage cache. It requires an exact match for build ID, application/manifest format, cache name, complete-build marker, offline-set digest and required-asset count. Only a different, marker-verified build reaches `complete-update-waiting`. The ordinary UI shows the human version (`v0.31.0`), while exact build IDs remain diagnostics.

### 21.2 User-confirmed activation and quiescence

The quiet card says **A new version of RosterBot is ready** and offers **Update now** or **Not now**. It remains in normal document flow rather than overlaying the interface, so it cannot obstruct mobile navigation, diary save actions or other ordinary work. Dismissal affects only the current page lifetime.

Update now first suppresses new automatic Cloud work. A known in-flight Auth, attestation, reconciliation, restore or revision-checked save is allowed up to the existing bounded request window to settle; a still-busy operation fails the activation attempt safely instead of being aborted. Next, schema-5 persistence waits for the projection chain and active replacement transaction, performs a no-op-safe final projection verification, and requires an application-ready/non-blocked startup state. This may finish a real already-pending edit, but the update itself creates no generation. It neither requires a network connection nor manufactures a Cloud save.

The authoritative startup gate is `startupAllowed`. Completed recovery decisions may retain `userChoiceRequired` as audit history, so that historical field is not treated as a live incomplete transaction after application-ready.

### 21.3 Worker activation protocol and exact reload

The generated worker contains one guarded `skipWaiting()` call, reachable only through `ACTIVATE_THIS_COMPLETE_BUILD`. The request names the expected waiting build. The worker compares that ID to its immutable embedded build, reopens its own cache, revalidates the exact complete marker, records the previous build, notifies clients and only then accepts activation.

Ordinary installation still never invokes `skipWaiting()`. After `controllerchange`, every participating page queries the new controller and requires its exact target build ID and complete-cache state. It performs one in-memory-guarded reload only after that match. The reloaded document then passes the Phase 1 foundational coherence gate and signals `ROSTERBOT_BUILD_READY`; a prior capability attestation is not persisted across this reload, so Phase 4 Cloud eligibility is established normally.

### 21.4 Multiple clients and iOS fallback

Tabs coordinate through `BroadcastChannel('rosterbot-update-v1')`. When BroadcastChannel is unavailable, the active service worker relays the same non-personal protocol to all same-origin window clients. The initiating tab announces a prepare request, and responsive peers independently reach their persistence/Cloud safe boundary before activation.

Peer discovery is quiet for 650 ms and the bounded peer wait is eight seconds. A responsive peer that reports an unsafe boundary cancels activation. A suspended/background client that cannot answer by the deadline does not block indefinitely; the activated worker claims it, and `controllerchange` forces its exact-build verification/reload when WebKit or another browser resumes it before normal interaction continues. No coordination payload contains personal data, tokens or crypto material.

### 21.5 Previous-build retention and failure behavior

Activation records live under `.rosterbot/update/` inside the new build cache. Build A is retained while B activates and until B reports service-worker control, foundational coherence and application-ready. A B startup failure therefore leaves A's complete cache and all personal data untouched. The worker never mixes A files into B.

Automatic rollback to A after B has become the registered controller is not universally safe or portable: the B worker does not carry A's executable asset map, and composing the two would violate build coherence. A pre-ready failure is therefore a distinct application-update failure, not Data Recovery. The retained A cache supports inspection and a controlled fix-forward/recovery procedure; a later coherent worker can recover without clearing personal storage.

After successful B startup, conservative retirement runs only when there is at most one visible window client. It retains active B, previous known-good A and the newest other complete cache (which may be waiting C). Older proven-complete caches may then be removed. With multiple clients, retirement is deferred. Foreign incomplete caches are never treated as runnable and are left for a later provably safe cleanup rather than risking deletion of an in-progress install. This bounds the normal single-client case without interfering with an open old client.

### 21.6 Offline, pending Cloud state and update checks

If B downloaded while online, it can activate and cold-start entirely from its verified cache after connectivity disappears. Local generation and schema-5 bytes survive unchanged. Unsynced local generations remain the durable pending state; no HTTP body is queued or replayed. On later connectivity, B follows Phase 4: fresh session and capability attestation, remote fetch, canonical reconciliation and at most one revision-checked save.

The registration explicitly uses `updateViaCache: 'none'` so the worker script is revalidated rather than hidden behind an HTTP cache. The browser's normal registration check runs at application startup. A foreground opportunity checks only when six hours have elapsed; there is no polling timer. An optional explicit API remains available for diagnostics/manual checking.

### 21.7 Verification and Phase 6 boundary

Unit tests cover typed states, exact waiting-marker validation, refusal of wrong activation IDs, the sole explicit `skipWaiting` path, Cloud-before-local quiescence, unsafe-boundary rejection, previous-cache retention until ready proof, post-ready conservative retirement, zero personal-state access from Cache Storage, and all Phase 3 atomic-install/fetch rules.

Production and staging contacts are forbidden and observed as zero.
